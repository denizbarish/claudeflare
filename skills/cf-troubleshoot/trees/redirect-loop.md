# Redirect loop (ERR_TOO_MANY_REDIRECTS)

Symptom: the browser shows `ERR_TOO_MANY_REDIRECTS` or "The page isn't redirecting properly". A request is redirected back and forth between two URLs, usually `http://` and `https://` of the same host, or two hosts.

## Evidence

1. Follow the chain from outside, both schemes, without cookies:
   ```
   curl -sI http://example.com/
   curl -sI https://example.com/
   curl -sIL --max-redirs 10 https://example.com/ | grep -iE "^HTTP|^location|^server|^cf-ray"
   ```
   For each hop note the status, `location` and `server`. A redirect from `https://example.com/` to the same `https://example.com/` (or to `http://`) shows the loop.
2. Who issues each hop: a hop generated by a Cloudflare redirect (Always Use HTTPS, Redirect Rules, Page Rules) never reaches the origin. A hop the origin issues passes through and typically carries origin headers (for example `x-powered-by`, or an app-specific `location` format). Compare with a direct origin request, only with an origin IP the user provides:
   ```
   curl -sI --resolve example.com:443:ORIGIN_IP https://example.com/
   curl -sI --resolve example.com:80:ORIGIN_IP http://example.com/
   ```
3. Settings and redirect rules:
   ```js
   async () => {
     const ssl = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/settings/ssl" });
     const https = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/settings/always_use_https" });
     const hsts = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/settings/security_header" });
     const pagerules = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/pagerules" });
     return { ssl: ssl.result, https: https.result, hsts: hsts.result, pagerules: pagerules.result };
   }
   ```
   Read separately (404 means no rules): `/zones/ZONE_ID/rulesets/phases/http_request_dynamic_redirect/entrypoint` (Single Redirects) and `/zones/ZONE_ID/rulesets/phases/http_config_settings/entrypoint` (per-path SSL mode overrides).
4. Start time and changes: audit log from SKILL.md. Typical triggers: the domain was just added to Cloudflare, SSL mode changed, a new redirect rule, or an origin plugin that forces HTTPS.

## Hypotheses

1. **Flexible mode plus an origin that forces HTTPS** (most common). Under Flexible, Cloudflare reaches the origin over HTTP; the origin redirects to `https://`, the browser asks Cloudflare over HTTPS again, and so on. Confirm: `ssl` is `flexible` (zone or a Configuration Rule for the path) and `curl -sI https://example.com/` returns 301 or 302 to `https://example.com/` itself; the direct `http://` origin request also redirects to `https://`. Reject: `ssl` is `full` or `strict`. This is `rules.redirect.loop_risk` in cf-rules.
2. **Full or Full (strict) plus an origin that redirects HTTPS to HTTP.** Confirm: `ssl` is `full` or `strict`, the `https://` response redirects to `http://`, and Always Use HTTPS (or HSTS) sends it back. Reject: origin does not redirect to `http://`.
3. **Always Use HTTPS plus an origin that redirects HTTPS to HTTP.** Confirm: `always_use_https` is `on`, `http://` gets a Cloudflare 301 to `https://`, which the origin redirects back to `http://`. Reject: origin never redirects to `http://`.
4. **HSTS with encryption mode Off, or with an origin redirecting to HTTP.** Confirm: `strict_transport_security.enabled` is `true` and `ssl` is `off`, or the origin redirects HTTPS to HTTP. Reject: neither.
5. **Conflicting redirect rules** (Redirect Rules or Page Rules sending A to B and B back to A, for example apex to www and www to apex, or a rule redirecting to `https://` without a scheme condition). Confirm: two rules whose targets match each other's conditions; the hop is Cloudflare-generated. Reject: no rule matches the looping URLs. See `rules.redirect.chain` in cf-rules.

## Fix

- Hypothesis 1: fix the encryption mode, not the redirects. If the origin has a valid certificate, plan `ssl` to `strict` (cf-ssl, finding `ssl.mode.flexible`; that plan sets `ssl_automatic_mode` to `custom` first when it is `auto`). If the origin has no certificate yet, the user installs one first (a Cloudflare Origin CA certificate works for Full (strict)); switching without it returns 525 or 526. The user may instead remove the origin HTTPS redirect and rely on Always Use HTTPS at the edge, but that keeps Flexible, which cf-ssl rates critical.
- Hypotheses 2 and 3 (origin side), steps for the user: remove the HTTPS to HTTP redirect at the origin (web server config, `.htaccess`, CMS site URL set to `http://`). For WordPress, set the site address to `https://`; the Cloudflare WordPress plugin with Automatic HTTPS Rewrites also helps. Turning off Always Use HTTPS is possible (reversible `zone_setting`), but fix the origin instead.
- Hypothesis 4: set `ssl` to at least `full` (prefer `strict`), or disable HSTS with `max_age: 0` (see the HSTS traps in cf-ssl: browsers keep the old policy until it expires).
- Hypothesis 5: remove or fix one of the conflicting rules (reversible `rule_update` or `rule_delete`, cf-rules); never create Page Rules.
- Verify: `curl -sIL --max-redirs 10 https://example.com/` ends in a 200 after at most one redirect, and `curl -sI http://example.com/` returns a single 301 to `https://`.
