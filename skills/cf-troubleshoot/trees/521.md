# Error 521: web server is down

Symptom: Cloudflare error page "Error 521", HTTP status 521. The origin refused the connection from Cloudflare (TCP connection refused or reset), so no request reached the web server.

## Evidence

1. Confirm and scope:
   ```
   curl -sI https://example.com/
   curl -sI http://example.com/
   ```
   Expect `521` with `server: cloudflare` and `cf-ray`. Check other proxied hostnames on the same origin: all down points to the server, one down points to a vhost or record.
2. Encryption mode decides the origin port (Flexible uses port 80, Full and Full (strict) use port 443), and Origin Rules can change host or port:
   ```js
   async () => {
     const ssl = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/settings/ssl" });
     const records = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/dns_records", query: { name: "example.com" } });
     return { ssl: ssl.result, records: records.result };
   }
   ```
   Also read `/zones/ZONE_ID/rulesets/phases/http_request_origin/entrypoint` in a separate call (404 means no Origin Rules) and look for `origin.port` or `host_header` overrides.
3. Start time and changes: status query and audit log from SKILL.md. Look for a change of `ssl` (for example Flexible to Full), DNS record content or Origin Rules just before the start.
4. Direct origin check, only with an origin IP the user provides, on the port the mode uses:
   ```
   curl -sv --resolve example.com:443:ORIGIN_IP https://example.com/ -o /dev/null
   curl -sv --resolve example.com:80:ORIGIN_IP http://example.com/ -o /dev/null
   ```
   `Connection refused` from your machine means nothing listens on that port or the host rejects everyone. A timeout from your machine may simply mean the origin firewall accepts only Cloudflare IPs.

## Hypotheses

1. **Web server process is down or crashed.** Confirm: every hostname on that origin returns 521, direct request gets `Connection refused` on both ports; the user's host shows the service stopped. Reject: direct request returns HTTP.
2. **Origin firewall or security software blocks Cloudflare IPs** (refuses or resets them). Confirm: direct request from your machine works while Cloudflare gets 521; the user confirms a firewall, fail2ban, mod_security or hosting "DDoS protection" that recently blocked IPs. Reject: the user confirms every range from https://www.cloudflare.com/ips/ is allowed.
3. **Nothing listens on the port the mode needs.** Confirm: `ssl` is `full` or `strict` and the port 443 direct request is refused while port 80 works, or an Origin Rule points to a port the origin does not serve. Reject: the needed port answers.
4. **DNS record points to the wrong server.** Confirm: the A or AAAA content differs from the origin IP the user gives, or the audit log shows a recent record change. Reject: content matches the current server.

## Fix

- Hypothesis 1 (origin side), steps for the user: start the web server (`systemctl status nginx` or `apache2`, then `systemctl start ...` on their server), read its error log for why it stopped, and check disk space and memory.
- Hypothesis 2 (origin side): allow every IPv4 and IPv6 range from https://www.cloudflare.com/ips/ in iptables, ufw, firewalld, the cloud security group and any security plugin; remove Cloudflare IPs from fail2ban or deny lists; never rate limit those ranges at the origin.
- Hypothesis 3: either the user enables HTTPS on port 443 with a valid certificate (Cloudflare Origin CA is fine for Full (strict)), or fix the Origin Rule port with a reversible `rule_update`. Do not switch to Flexible as a fix (see cf-ssl, finding `ssl.mode.flexible`).
- Hypothesis 4: plan a reversible `dns_update` with the correct IP (cf-dns), after the user confirms the address:
  ```json
  { "method": "PATCH", "path": "/zones/{zone_id}/dns_records/RECORD_ID", "body": { "content": "203.0.113.10" } }
  ```
- Verify: `curl -sI https://example.com/` returns the expected status with `cf-ray`; 521 disappears in the status query.
