# Errors 525 and 526: SSL handshake failed, invalid SSL certificate

Symptom: Cloudflare error page "Error 525" (SSL handshake failed) or "Error 526" (invalid SSL certificate). Both concern the connection from Cloudflare to the origin, not the visitor's certificate.

- **525**: the TLS handshake between Cloudflare and the origin failed, with the encryption mode set to Full or Full (strict).
- **526**: Cloudflare could not validate the origin certificate, with the encryption mode set to Full (strict).

## Evidence

1. Confirm which error, and that the edge certificate is fine:
   ```
   curl -sI https://example.com/
   openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | grep -E "subject=|issuer=|Verify return code"
   ```
   The second command shows the edge certificate Cloudflare serves to visitors; a valid one here proves the problem is on the origin side.
2. Effective encryption mode, including per-path overrides:
   ```js
   async () => {
     const ssl = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/settings/ssl" });
     const config = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/rulesets/phases/http_config_settings/entrypoint" });
     return { ssl: ssl.result, config: config.result };
   }
   ```
   If the entrypoint returns 404 (no Configuration Rules) the call fails; read `ssl` alone. Also read `ssl_automatic_mode` (see cf-ssl) and the Origin Rules entrypoint `http_request_origin` for port overrides.
3. Start time and changes: status query and audit log from SKILL.md. Typical triggers: `ssl` changed to `strict`, Automatic SSL/TLS upgraded the mode, or the origin certificate expired on a known date.
4. Origin certificate, only with an origin IP the user provides:
   ```
   openssl s_client -connect ORIGIN_IP:443 -servername example.com </dev/null 2>/dev/null | grep -E "Verify return code|Protocol|Cipher"
   openssl s_client -connect ORIGIN_IP:443 -servername example.com </dev/null 2>/dev/null | openssl x509 -noout -text | grep -E "Subject:|Issuer:|Not After|DNS:"
   ```
   No certificate or a handshake failure points to 525; an expired date, a missing hostname in `DNS:` entries, a self-signed issuer or a verify error points to 526. A Cloudflare Origin CA certificate shows a verify error from your machine (only Cloudflare trusts it) but is valid for Full (strict). If the origin firewall accepts only Cloudflare IPs, these commands time out; ask the user to run them from an allowed host or check with their host.

## Hypotheses

For 525:

1. **No certificate or no TLS on port 443** (origin serves only HTTP, or 443 is closed). Confirm: origin handshake fails or connection refused on 443 while port 80 works; often right after switching from Flexible. Reject: origin presents a certificate.
2. **No SNI support or wrong vhost for the hostname.** Confirm: handshake fails or a default certificate appears with `-servername example.com` but works for another name. Reject: correct certificate for the SNI name.
3. **No common cipher suite or protocol.** Confirm: the `Protocol` or `Cipher` line is empty or the user's server allows only old ciphers or only TLS versions Cloudflare does not offer. Reject: modern TLS 1.2 or 1.3 negotiated.
4. **Intermittent resets during handshake** (overload, firewall). Confirm: 525 only some of the time; the user's TLS error log (nginx `error.log`, Apache mod_ssl log) shows resets at those times. Reject: steady failures.

For 526:

1. **Expired certificate.** Confirm: `Not After` in the past. Automatic SSL/TLS never downgrades, so an expiry under Full (strict) stays 526 until renewal. Reject: date valid.
2. **Hostname not in the certificate.** Confirm: `example.com` (or a matching wildcard) missing from the `DNS:` entries. Reject: listed.
3. **Self-signed or untrusted issuer, or incomplete chain.** Confirm: issuer is the server itself or an unknown CA, or the origin does not send the intermediate certificate. Reject: public CA or Cloudflare Origin CA with full chain.
4. **Configuration Rule forces strict on some paths.** Confirm: a rule in `http_config_settings` sets `ssl: "strict"` for the failing paths while the zone is `full`. Reject: no such rule.

## Fix

- Origin side, steps for the user (both errors):
  1. Install a valid certificate for the hostname: a public CA certificate (for example Let's Encrypt), or a free Cloudflare Origin CA certificate (SSL/TLS, Origin Server, Create Certificate in the dashboard), installed with the full chain.
  2. Make the web server listen on 443 with SNI for the hostname (nginx `listen 443 ssl;` with `server_name example.com;` and `ssl_certificate` pointing to the full chain file; Apache `SSLCertificateFile` plus chain in the matching vhost).
  3. Enable TLS 1.2 and 1.3 with modern ciphers; reload the web server; renew before expiry (automate renewal).
- A self-signed certificate can instead be uploaded to the Custom Origin Trust Store so Full (strict) accepts it.
- Temporary workaround for 526 only, after the user accepts the risk (origin certificate no longer validated): set `ssl` to `full` with a reversible `zone_setting` plan, and switch back to `strict` once the certificate is fixed (cf-ssl, finding `ssl.mode.full_not_strict`). If `ssl_automatic_mode` is `auto`, set it to `custom` first in the same plan, as cf-ssl shows. Never switch to Flexible as a fix (cf-ssl, finding `ssl.mode.flexible`).
- Hypothesis "Configuration Rule forces strict": fix the rule with a reversible `rule_update`.
- Verify: `curl -sI https://example.com/` returns the expected status; 525 or 526 rows disappear in the status query.
