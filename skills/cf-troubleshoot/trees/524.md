# Error 524: a timeout occurred

Symptom: Cloudflare error page "Error 524", HTTP status 524. Cloudflare connected to the origin and sent the request, but the origin did not send an HTTP response before the Proxy Read Timeout (125 seconds by default). A 524 can also mean the write to the origin did not finish within the 30 second Proxy Write Timeout, which cannot be changed.

## Evidence

1. Confirm, and time the request:
   ```
   curl -s -o /dev/null -w "%{http_code} %{time_total}\n" https://example.com/slow/path
   ```
   A 524 arrives after about 125 seconds (or the zone's configured timeout). Note which paths fail: exports, reports, imports and large uploads are typical.
2. Which paths and when: status query from SKILL.md; 524 rows by `clientRequestPath` show whether it is one slow endpoint or the whole site.
3. Current timeout and plan:
   ```js
   async () => {
     const timeout = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/settings/proxy_read_timeout" });
     return timeout.result;
   }
   ```
   Read the plan tier from the zone object (cf-core discovery). Changing the timeout is Enterprise only; on other plans the read may fail or show the default, so skip it there.
4. Direct origin timing, only with an origin IP the user provides:
   ```
   curl -s -o /dev/null -w "%{http_code} %{time_starttransfer}\n" --resolve example.com:443:ORIGIN_IP https://example.com/slow/path
   ```
   `time_starttransfer` above the timeout confirms the origin itself is slow.
5. Start time and changes: audit log from SKILL.md for the window where 524s started (for example a lowered `proxy_read_timeout`).

## Hypotheses

1. **Long-running request at the origin** (large query, export, report, synchronous job). Confirm: 524 only on specific paths; direct `time_starttransfer` above 125 seconds; the origin access log (the user can add response time to the log format) shows long durations. Reject: the same path answers fast directly.
2. **Overloaded origin** (all requests slow under load). Confirm: 524 across many paths, rising with traffic; the user's monitoring shows CPU, database or worker saturation. Reject: origin load normal during the errors.
3. **Slow upload or write to the origin** (request body not accepted within 30 seconds). Confirm: 524 on large `POST` or `PUT` uploads only. Reject: failing requests are small `GET`s.
4. **Timeout lowered on Enterprise.** Confirm: `proxy_read_timeout` value below 125, or a Cache Rule sets a lower Proxy Read Timeout on the path; the audit log shows the change. Reject: default value and no such rule.

## Fix

- Hypothesis 1 (origin side), steps for the user: make the slow request asynchronous (start the job, return immediately, let the client poll a status URL), add pagination or streaming, or optimize the query.
- Hypothesis 2 (origin side): scale the origin or fix the bottleneck; caching static content reduces load (cf-cache, finding `cache.rules.none_for_static`).
- Hypothesis 3: the user makes uploads go directly to storage (for example presigned URLs) or to a DNS-only hostname.
- Requests that regularly need more than 125 seconds on a non-Enterprise plan: move them to a subdomain that is DNS-only (not proxied). Creating such a record is a reversible `dns_create` plan (cf-dns); state in the risk note that this hostname gets no Cloudflare protection and exposes the origin IP (`dns.proxy.origin_exposed`).
- Enterprise only, raise the timeout (reversible `zone_setting`, up to 6000 seconds; set one second more than needed):
  ```json
  { "method": "PATCH", "path": "/zones/{zone_id}/settings/proxy_read_timeout", "body": { "value": 300 } }
  ```
  Or per path, a Cache Rule with the Proxy Read Timeout setting (the request must be eligible for cache for the rule to apply, not actually cached).
- Verify: the timing command returns the expected status under the timeout; 524 disappears in the status query.
