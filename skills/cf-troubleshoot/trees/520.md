# Error 520: web server returns an unknown error

Symptom: Cloudflare error page "Error 520", HTTP status 520. Cloudflare reached the origin, but the origin returned an empty, unknown or unexpected response (for example the connection was closed before response headers, or the headers were malformed or too large).

## Evidence

1. Confirm the error comes from Cloudflare and note the `cf-ray`:
   ```
   curl -sI https://example.com/
   ```
   Expect `HTTP/2 520`, `server: cloudflare`, `cf-ray`. Repeat on two or three paths and once with and without a cookie-heavy session to see whether it is site-wide or path-specific.
2. Edge versus origin status per path: run the status query from SKILL.md (Shared evidence). Note for 520 rows whether `originResponseStatus` is 0 (no HTTP response parsed) or a normal code such as 200 (response arrived but was malformed, for example oversized headers).
3. Start time and changes: the first bucket with 520 rows, then the audit log for that window (SKILL.md).
4. Zone features that change how Cloudflare talks to the origin:
   ```js
   async () => {
     const ssl = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/settings/ssl" });
     const aop = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/settings/tls_client_auth" });
     return { ssl: ssl.result, aop: aop.result };
   }
   ```
   `tls_client_auth` `on` means zone-level Authenticated Origin Pulls is enabled.
5. Direct origin check, only with an origin IP the user provides (it can fail if the origin firewall only accepts Cloudflare IPs; that is expected and not evidence of a crash):
   ```
   curl -sv --resolve example.com:443:ORIGIN_IP https://example.com/ -o /dev/null
   curl -sv --http1.1 --resolve example.com:443:ORIGIN_IP https://example.com/ -o /dev/null
   ```
   Look for `Empty reply from server`, a reset during headers, a response without a status line, or a very large `set-cookie` block. If HTTP/1.1 works and the default (HTTP/2 via ALPN) fails, the origin's HTTP/2 is broken.

## Hypotheses

1. **Origin application crashes or closes the connection** (most common, often PHP or an app server behind a proxy). Confirm: `originResponseStatus` 0 on the 520 rows, direct request shows `Empty reply from server` or a reset; the user's origin error log shows crashes at the same times. Reject: direct request returns a complete response every time.
2. **Response headers exceed 128 KB**, usually from many or large cookies. Confirm: 520 only for logged-in users or specific paths; origin status 200 while edge status is 520; direct request shows a very large header block. Reject: header size small (a few KB) on the failing path.
3. **Origin firewall or security plugin drops some Cloudflare IPs** (resets instead of refusing). Confirm: intermittent 520 across all paths, failures cluster in some data centers (`cf-ray` suffix differs between failing and working requests); the user confirms a firewall, fail2ban or security plugin. Reject: the origin allowlists all ranges from https://www.cloudflare.com/ips/.
4. **Broken HTTP/2 at the origin.** Cloudflare uses HTTP/2 to the origin when the origin offers it through ALPN; an origin that accepts h2 but mishandles it returns 520. Confirm: the `--http1.1` request works while the default fails. Reject: both behave the same.
5. **Authenticated Origin Pulls mismatch.** Confirm: `tls_client_auth` is `on` (or per-hostname AOP is configured) and the audit log or the user shows a recent change to it or to the origin's client certificate check. Reject: AOP off and no client-certificate check at the origin.
6. **Idle keep-alive connection closed by the origin.** Cloudflare reuses origin connections for up to 900 seconds of idle time; an origin or middlebox closing them earlier can cause sporadic 520. Confirm: rare, scattered 520 with no path pattern while the origin is healthy. Reject: errors are steady or path-specific.

## Fix

- Hypotheses 1 to 3 (origin side), give the user these steps:
  1. Check the web server and application error logs (nginx `error.log`, Apache `error_log`, PHP-FPM log) at the times of the 520 rows; fix the crash or raise the worker or memory limits.
  2. For large headers: reduce cookie count and size in the application.
  3. Allow every Cloudflare range from https://www.cloudflare.com/ips/ (IPv4 and IPv6) in the host firewall, iptables or ufw, fail2ban and security plugins; never rate limit those ranges.
  4. Make the origin always send a status line and headers, including on errors.
- Hypothesis 4: fix the origin's HTTP/2 configuration (user step). As a workaround, HTTP/2 to Origin can be turned off: find the setting id with the MCP `search` tool and plan a reversible zone setting PATCH; if it is not exposed in the API, tell the user the dashboard path (Speed, Settings, Protocol Optimization, HTTP/2 to Origin).
- Hypothesis 5: configure the origin to accept the Cloudflare client certificate (user step), or plan `{ "method": "PATCH", "path": "/zones/{zone_id}/settings/tls_client_auth", "body": { "value": "off" } }` only if the user confirms the origin does not require it.
- Hypothesis 6: the user sets the origin keep-alive timeout above 900 seconds or stops intermediaries from dropping idle connections.
- Verify: `curl -sI https://example.com/` returns the expected status with `cf-ray`, and 520 rows disappear in the status query.
