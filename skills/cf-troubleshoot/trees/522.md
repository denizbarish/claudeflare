# Error 522: connection timed out

Symptom: Cloudflare error page "Error 522", HTTP status 522. Cloudflare timed out contacting the origin: either no SYN+ACK arrived within 19 seconds of the first SYN, or after the TCP connection was set up the origin did not acknowledge the request within 90 seconds.

## Evidence

1. Confirm and scope:
   ```
   curl -sI https://example.com/
   ```
   Expect `522`, `server: cloudflare`, `cf-ray`. Try a second path and a second proxied hostname on the same origin.
2. DNS record and origin overrides:
   ```js
   async () => {
     const records = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/dns_records", query: { name: "example.com" } });
     const ssl = await cloudflare.request({ method: "GET", path: "/zones/ZONE_ID/settings/ssl" });
     return { records: records.result, ssl: ssl.result };
   }
   ```
   Read `/zones/ZONE_ID/rulesets/phases/http_request_origin/entrypoint` separately (404 means no Origin Rules). Ask the user whether the hostname is a Pages project or a Worker on a Custom Domain.
3. Start time and pattern: status query from SKILL.md. Steady 522 on everything points to a block or wrong IP; 522 that grows with traffic points to an overloaded origin. Then the audit log for the start window.
4. Direct origin check, only with an origin IP the user provides:
   ```
   curl -sv --connect-timeout 20 --resolve example.com:443:ORIGIN_IP https://example.com/ -o /dev/null
   ```
   If it connects from your machine, the server is up and Cloudflare is the one being dropped. If it also times out, the origin may allow only Cloudflare IPs (expected) or be down; the user's host must check.

## Hypotheses

1. **Origin firewall drops or rate limits Cloudflare IPs** (most common per Cloudflare). Confirm: direct request connects from your machine while Cloudflare gets 522; the user finds Cloudflare ranges in a deny list, iptables DROP rule, `.htaccess` deny, or a host "DDoS protection" that rate limits; errors started when a firewall rule changed. Reject: the user confirms every range from https://www.cloudflare.com/ips/ is allowed and not rate limited.
2. **DNS record points to an old or wrong IP.** Confirm: record content differs from the IP the host currently assigns to the server (ask the user), or the audit log shows a record change, or the server moved recently. Reject: content matches.
3. **Origin overloaded or offline, dropping connections.** Confirm: 522 count rises with request volume, or the user's monitoring shows CPU, memory or connection limits hit; the host reports packet loss. Reject: origin load normal during the errors.
4. **Keep-alives disabled at the origin.** Confirm: the user's web server config has keep-alive off (nginx `keepalive_timeout 0`, Apache `KeepAlive Off`). Reject: keep-alive on.
5. **Pages or Workers specifics.** Confirm: a Pages hostname that is not added as a custom domain in the Pages project, or whose CNAME does not point to `<project>.pages.dev`; or a Worker on a Custom Domain that `fetch`es its own hostname; or an Origin Rule sending traffic to a hostname that resolves to a reserved address such as `192.0.2.0` or `100::`. Reject: none of these apply.

## Fix

- Hypothesis 1 (origin side), steps for the user:
  1. Allow every IPv4 and IPv6 range from https://www.cloudflare.com/ips/ in the server firewall (iptables, ufw, firewalld), cloud security group, `.htaccess` and security plugins.
  2. Remove any rate limit or connection limit that applies to those ranges.
  3. To restrict visitors by country or IP, use a Cloudflare WAF custom rule instead of blocking at the origin (see cf-waf).
- Hypothesis 2: plan a reversible `dns_update` with the address the user confirms (cf-dns):
  ```json
  { "method": "PATCH", "path": "/zones/{zone_id}/dns_records/RECORD_ID", "body": { "content": "203.0.113.10" } }
  ```
- Hypothesis 3: the user scales the origin or fixes the slow component; caching static content takes load off it (cf-cache, finding `cache.rules.none_for_static`).
- Hypothesis 4: the user enables keep-alive in the web server.
- Hypothesis 5: set up the Pages custom domain in the Pages project; for a Worker calling its own hostname, use a Route, another hostname, or the `global_fetch_strictly_public` compatibility flag; fix the Origin Rule target (reversible `rule_update`).
- If none confirms, ask the user for an MTR or traceroute from the origin to a Cloudflare IP seen in the origin logs, for their host or Cloudflare Support.
- Verify: `curl -sI https://example.com/` returns the expected status; 522 disappears in the status query.
