# Error 1102: CPU or memory limit exceeded

Symptom: Cloudflare error page "Error 1102" with "Worker exceeded resource limits". Invocation status `exceededResources`; tail and analytics outcome `exceededCpu` (CPU time) or `exceededMemory` (memory). For memory, continue in [memory-limit.md](memory-limit.md).

## Evidence

1. Which limit:
   ```
   claudeflare tail --worker api --seconds 30 --status error
   ```
   `outcomes` shows `exceededCpu` or `exceededMemory`. Note the request paths in `samples`.
2. CPU profile over time: the GraphQL query from SKILL.md, `cpuTimeP50` and `cpuTimeP99` per status, and the `exceededResources` count. A high P99 with a normal P50 points to a few heavy requests.
3. Plan and limit: Workers Free has 10 ms CPU per HTTP request; Workers Paid defaults to 30 seconds and allows up to 5 minutes through `limits.cpu_ms` in the wrangler config. Read `limits` in the wrangler file and ask the user which Workers plan the account has.
4. What changed: `wrangler deployments list --name api --json` (new version, new dependency, larger payloads).

## Hypotheses

1. **CPU-heavy code path.** Confirm: `exceededCpu` on specific paths (large JSON parse, crypto, image or HTML processing, server-side rendering, tight loops); P99 CPU near the limit. Reject: CPU percentiles far below the limit.
2. **Limit too low for the plan.** Confirm: Workers Free with a workload that needs more than 10 ms, or a `limits.cpu_ms` set lower than the workload needs. See cf-workers finding `workers.cpu_limit.near`. Reject: limit already at the maximum the plan allows.
3. **Regression in a new version.** Confirm: `exceededCpu` starts at a deployment. Reject: errors predate it.
4. **Memory, not CPU.** Confirm: `exceededMemory` in outcomes. Go to [memory-limit.md](memory-limit.md).
5. **Cron, Queue or Durable Object alarm handler.** Confirm: errors come from a scheduled or queue invocation, which have their own CPU and duration limits (Cron Triggers 30 seconds CPU below a 1 hour interval, 15 minutes at 1 hour or more). Reject: only HTTP invocations fail.

## Fix

- Hypothesis 3: a rollback plan to the last good version (cf-core): `{ "kind": "wrangler", "args": ["rollback", "<version-id>", "--name", "api"] }`.
- Hypothesis 2 on Workers Paid: suggest raising `limits.cpu_ms` in the wrangler file (for example `"limits": { "cpu_ms": 300000 }`, maximum 5 minutes), then a deploy plan. On Workers Free, the options are optimizing or upgrading to Workers Paid (user decision).
- Hypothesis 1: suggest code changes: profile with DevTools CPU profiling in `wrangler dev`, cache computed results (KV, Cache API), stream instead of parsing whole bodies, split work across requests, Queues or Durable Objects.
- Verify: no `exceededCpu` in the tail during a repeat of the heavy request; `exceededResources` drops to zero in GraphQL.
