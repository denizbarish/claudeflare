# Error 1042: fetch to another Worker on the same zone

Symptom: error 1042, or a Worker's `fetch()` to a URL on its own zone that should hit another Worker fails or reaches the origin instead. Without the `global_fetch_strictly_public` compatibility flag, a global `fetch()` to another Worker on the same zone (on a route or `workers.dev`) is not supported. 1042 is also returned for a `workers.dev` URL with no Worker serving it, for example a Worker whose `workers.dev` route is disabled.

## Evidence

1. The calling code: the URL passed to `fetch()` and its hostname. Ask the user, or read the project.
2. The calling Worker's config: `compatibility_flags` in the wrangler file for the deployed environment, and `services` bindings.
3. How the target Worker is reached: its `routes` (route pattern on the same zone), Custom Domain, or `workers_dev`. Read the target project's wrangler file, or ask the user.
4. Outside check of the target URL (read-only):
   ```
   curl -sI https://api.example.com/health
   ```
   A response from the target Worker proves it serves that hostname from the Internet.
5. Tail of the caller during a repeat: `claudeflare tail --worker caller --seconds 30 --status error`.

## Hypotheses

1. **Same-zone fetch to a Worker on a route, without the flag or a service binding.** Confirm: caller and target share a zone; the target runs on a route; the caller has neither `global_fetch_strictly_public` nor a `services` binding to the target. Reject: different zones, or the target is on a Custom Domain (same-zone fetch to a Custom Domain works).
2. **`workers.dev` URL with no Worker.** Confirm: the URL is `*.workers.dev` and the target has `workers_dev: false`, or the name is wrong. Reject: the target serves that `workers.dev` URL (curl).
3. **Fetch reaches the origin instead of the Worker.** Confirm: without the flag, a same-zone request goes to the zone's origin and skips Workers on that URL and the zone's security settings; the response comes from the origin. Reject: the response is from the target Worker.

## Fix

- Hypothesis 1, preferred: suggest a service binding in the caller's wrangler file and calling `env.TARGET.fetch(request)` instead of the public URL:
  ```jsonc
  "services": [{ "binding": "TARGET", "service": "target-worker" }]
  ```
  Then a deploy plan for the caller (cf-core). The call stays inside Cloudflare and skips the Internet.
- Hypothesis 1, alternative: add `global_fetch_strictly_public` to `compatibility_flags` (cf-workers finding `workers.global_fetch.missing`), then a deploy plan. The request then goes through the zone's front door like an Internet request: WAF and other rules apply, and a Worker calling its own route can loop back to itself (up to the 16-invocation loop limit, error 1019).
- Hypothesis 1, other: move the target to a Custom Domain (cf-workers).
- Hypothesis 2: fix the URL, or enable the target's `workers.dev` route only if it should be public (cf-workers finding `workers.routes.unprotected_workers_dev`).
- Verify: the caller's tail shows no exceptions during a repeat; the response comes from the target Worker.
