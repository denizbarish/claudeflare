# Error 1101: Worker threw exception

Symptom: Cloudflare error page "Error 1101", or a 500 from a Worker or Pages Function. The Worker threw an uncaught JavaScript exception, or finished without returning a Response ("The script will never generate a response"). Invocation status `scriptThrewException`, tail outcome `exception`.

## Evidence

1. Exceptions live:
   ```
   claudeflare tail --worker api --seconds 30 --status error
   ```
   Read `top_exceptions` (name and message) and the `samples` (request status, logs before the throw). Ask the user to repeat the failing request during the tail.
2. Start time and share of traffic: the GraphQL query from SKILL.md; `scriptThrewException` count against total `requests`.
3. What changed: `wrangler deployments list --name api --json`. Note the version deployed just before the first errors, and whether a split deployment is active (`wrangler deployments status --name api --json`).
4. Config: bindings and `compatibility_date`, `compatibility_flags` in the wrangler file for the deployed environment; `wrangler versions view <version-id> --name api --json` for the deployed version.
5. Stack traces with original file names need source maps (`upload_source_maps`); without them, ask the user to reproduce with `wrangler dev`.

## Hypotheses

1. **Bug in a new version.** Confirm: errors start at a deployment; the exception points to code changed in that version. Reject: errors predate the latest deployment.
2. **Binding or variable undefined** (`TypeError: Cannot read properties of undefined (reading 'get')` or similar on `env.X`). Confirm: the binding name in the exception is missing from the deployed version or from that `env` block. Go to [missing-binding.md](missing-binding.md).
3. **Upstream response not handled.** Confirm: the exception follows a `fetch()`, D1, KV or R2 call (for example JSON parse of an error page, a D1 `no such table` after a deploy that needed a migration). For D1 schema errors check `wrangler d1 migrations list <db> --remote` (cf-storage, `d1.migrations.pending`). Reject: the failing line has no I/O.
4. **"The script will never generate a response".** Confirm: that message in the exception; the code awaits a Promise that never settles, or a WebSocket is never closed. Reject: another exception message.
5. **Compatibility date or flag change.** Confirm: the failing version changed `compatibility_date` or `compatibility_flags`, and the error matches a documented behavior change. Reject: unchanged.

## Fix

- Hypothesis 1 and 5, immediate: a rollback plan to the last good version (cf-core account plan):
  ```json
  { "kind": "wrangler", "args": ["rollback", "<last-good-version-id>", "--name", "api"] }
  ```
  Rollback is refused if a bound resource was deleted or a Durable Object lifecycle change happened since; data is not rolled back. Then suggest the code fix to the user and deploy it through a plan with a `health_check`.
- Hypothesis 2: see [missing-binding.md](missing-binding.md).
- Hypothesis 3: suggest checks on `response.ok` and try/catch around the call, returning a proper error Response; for D1, plan the pending migration (cf-storage) before the code that needs it.
- Hypothesis 4: suggest resolving or rejecting the Promise, closing the WebSocket, and returning a Response on every path.
- Optional for proxy Workers: `ctx.passThroughOnException()` forwards requests to the origin on an uncaught exception; it hides errors, so only as a stopgap the user chooses.
- Verify: the tail shows no `exception` outcomes while the user repeats the request; `scriptThrewException` drops to zero in GraphQL.
